## 문제

ADR 0002는 통역 파이프라인을 참가자별 로컬 실행으로 두었다. 그 결정의 대가를 같은 문서에 이렇게 적었다.

> 참가자마다 Python 환경과 API 키가 필요하다. 개발자가 아닌 참가자는 이 방식으로 참여할 수 없다.
> 데모할 때 각자 터미널을 띄워야 한다. 브라우저만으로 완결되지 않는다.

배포한 사이트에서 회의에 들어가도 자막이 나오지 않는다. 참가자 다섯이면 터미널 다섯 개를 각자 띄워야 한다. 발표 자리에서 성립하지 않는 방식이고, ADR 0002가 정한 재검토 조건에 그대로 걸린다.

## 결정

**회의방에 참가해 참가자 전원을 통역하는 에이전트를 만들고, 프로세스 하나로 방 전체를 담당한다.**

```text
참가자 브라우저 -> LiveKit -> 에이전트 -> Deepgram -> 번역 -> Server
                                                                |
                                                    모든 참가자 화면
```

참가자는 브라우저만 열면 된다. 설치도 터미널도 API 키도 필요 없다.

에이전트는 구독만 하고 참가자 목록에 뜨지 않는다(`can_publish=False`, `hidden=True`). 회의 화면에 정체불명의 참가자가 보이면 안 되고, 통역은 듣기만 하면 된다.

**Client와 Server는 고치지 않는다.** 통역에 필요한 정보가 이미 LiveKit 참가자에 실려 있다.

| 필요한 것 | 어디서 |
| --- | --- |
| 자막의 `participantIdentity` | `participant.identity` |
| 표시 이름 | `participant.name` |
| 번역 방향 | `participant.attributes["preferredLanguage"]` |

`apps/server`가 토큰을 만들 때 넣어준 값이다. ADR 0002가 남긴 "화자 정보를 손으로 지정한다"는 제약이 함께 사라진다.

## 대안

| 대안 | 검토 결과 |
| --- | --- |
| 참가자별 로컬 실행 유지 (ADR 0002) | 배포 사이트에서 자막이 나오지 않는다. 위 문제 그대로다. |
| Server(NestJS)에서 오디오를 받아 처리 | 새 서비스를 띄우지 않아도 된다. 그러나 번역 로직이 Python이라 TypeScript로 다시 써야 한다. 관용구 지침, 조각 처리, 중간 번역과 테스트 313건을 버리게 된다. |
| `livekit-agents`의 STT 플러그인 사용 | 코드가 크게 준다. 그러나 Issue #72와 #76에서 만든 조각 유실 수정과 중간 번역이 플러그인 안으로 감춰져 무의미해진다. |
| **프레임워크로 방 배정만 받고 오디오는 원시로 처리** | 선택 |

## 결정 이유

- **기존 코드를 거의 그대로 쓴다.** 바뀌는 것은 오디오 입력뿐이다. `TranslationPipeline`, `TranslationSession`, 관용구 지침, `SubtitlePublisher`, 회의방 이름 생성은 손대지 않았다. 인식 경로도 `AudioSource` 하나를 주입 가능하게 바꾼 것이 전부다.
- **화자 분리는 여전히 공짜다.** 참가자마다 오디오 스트림이 따로 오므로 diarization이 필요 없다. ADR 0002가 로컬 실행을 택한 가장 큰 이유였는데, 에이전트 방식에서도 유지된다.
- **참가자마다 파이프라인을 따로 둔다.** 하나를 공유하면 번역 호출에 락이 걸려 두 사람이 동시에 말할 때 서로를 기다린다. 각자 프로세스로 돌리던 종전과 동작이 같다.
- **배포 경로가 생긴다.** LiveKit Cloud가 에이전트를 컨테이너로 호스팅하고, 무료 티어에 월 1,000 AI Agent 분이 포함된다. 지금 방식으로는 배포할 자리 자체가 없었다.

## 영향

- **참가자는 아무것도 설치하지 않는다.** ADR 0002의 가장 큰 제약이 없어진다.
- **터미널이 참가자 수만큼에서 하나로 준다.** 다만 그 하나는 여전히 누군가 켜둬야 한다.
- **단일 장애점이 생긴다.** 에이전트가 죽으면 **전원의** 자막이 멈춘다. 로컬 실행에서는 한 명이 꺼져도 그 사람 것만 안 떴다.
- **모든 참가자의 오디오가 에이전트를 지난다.** 대역폭과 CPU를 쓰고, 회의 음성이 그 기계를 경유한다.
- **LiveKit 무료 티어에서 에이전트도 참가자 1명으로 센다.** 5명 회의는 6명이 된다.
- **회의방만 받는다.** 에이전트는 방이 열리는 대로 배정받으므로, 가상 오피스처럼 회의가 아닌 방까지 따라 들어가면 쓸데없이 호출을 태운다. `is_lab_meeting_room()`으로 거른다.
- 의존성 두 개가 늘었다. `livekit`, `livekit-api`.

### 상시 호스팅은 아직이다

이 결정으로 코드는 배포 가능해졌지만 **아직 배포하지 않았다.** 지금은 누군가의 노트북에서 켜둔다. 그 상태로도 참가자는 브라우저만으로 자막을 보므로 문제의 핵심은 해결된다.

Render 백그라운드 워커는 월 $7이고 무료 티어 웹 서비스는 15분 후 잠들어 상시 대기에 맞지 않는다. LiveKit Cloud 배포는 계정 플랜과 배정 규칙을 확인한 뒤 별도로 판단한다.

### 검증된 범위

실제 회의방에서 브라우저만으로 자막이 나오는 것을 확인했다. 참가자 입장·퇴장과 워커 정리도 반복해서 확인했다.

**여러 명이 동시에 말하는 경우는 아직 확인하지 않았다.** ADR 0002에서 넘어온 미검증 항목이 그대로 남아 있다.

## 재검토 조건

- 에이전트가 죽었을 때 전원의 자막이 멈추는 것이 실제로 문제가 되는 경우
- 참가자가 많아져 한 프로세스가 감당하지 못하는 경우
- LiveKit Cloud 무료 티어의 에이전트 분을 다 쓰는 경우
- 번역 로직을 Server로 옮길 만큼 안정화되어 Python 프로세스를 없애는 것이 이득이 되는 시점
