## 문제

통역 파이프라인은 마이크 오디오를 받아 인식하고 번역해 자막을 만든다. 이 처리를 어디서 돌릴지 정해야 한다.

화상회의 자체는 LiveKit이 담당한다. 참가자는 브라우저로 회의방에 들어가고, 오디오와 비디오는 LiveKit을 통해 오간다. 통역 파이프라인은 이 흐름에 끼어들지 않고 자막만 별도로 만들어 Server로 보낸다.

선택지는 크게 둘이다. 서버가 LiveKit에서 오디오 트랙을 받아 모든 참가자의 발화를 처리하거나, 참가자가 각자 자기 PC에서 자기 마이크만 처리하거나.

## 결정

**참가자가 각자 자기 PC에서 `scripts/live_translate.py`를 실행한다.**

각 프로세스는 자기 마이크만 연다. 자기 발화를 인식하고 번역해 자막을 Server로 POST하면, Server가 회의방 구독자 전원에게 socket.io로 뿌린다.

```text
참가자 A PC   마이크 -> Deepgram -> 번역 -> POST /meeting/subtitles/mock
참가자 B PC   마이크 -> Deepgram -> 번역 -> POST /meeting/subtitles/mock
                                                      |
                                              Server broadcast
                                                      |
                                          모든 참가자의 회의 화면
```

Server와 Client는 자막을 받아 보여줄 뿐, 파이프라인이 어디서 돌았는지 모른다. LiveKit도 건드리지 않는다.

## 대안

| 대안 | 검토 결과 |
| --- | --- |
| 서버가 LiveKit 오디오 트랙을 구독해 처리 | 참가자는 브라우저만 열면 되므로 진입 장벽이 없다. 그러나 서버가 트랙마다 Deepgram 연결을 유지해야 하고, LiveKit 서버 SDK로 참가자를 붙여 트랙을 받는 구현이 필요하다. 무료 티어 한도를 한 계정이 전부 소비한다. |
| 서버가 LiveKit egress로 녹음을 받아 처리 | 구현이 단순하지만 녹음이 끝나야 처리하므로 실시간이 되지 않는다. 이 기능의 요구를 만족하지 못한다. |
| 브라우저에서 처리 | 설치가 필요 없다. 그러나 Deepgram API 키가 브라우저에 노출되고, 브라우저 내장 음성 인식으로 바꾸면 Nova-3의 한국어·베트남어 품질을 포기해야 한다. |
| 참가자별 로컬 실행 | 선택 |

## 결정 이유

- **화자 분리가 필요 없다.** 각 프로세스가 자기 마이크만 들으므로 누가 말했는지 이미 안다. 서버에서 한꺼번에 처리하면 화자 분리(diarization)를 하거나 트랙별로 인식 연결을 따로 관리해야 한다. 자막 계약이 `participantIdentity`를 요구하므로 이 정보는 반드시 필요하다.
- **네트워크 코덱을 거치지 않은 오디오를 쓴다.** 마이크에서 읽은 16kHz PCM을 그대로 Deepgram에 보낸다. 서버 방식은 WebRTC로 전송·복원된 오디오를 쓰게 된다. 인식 품질 차이는 측정하지 않았다.
- **무료 한도가 참가자별로 나뉜다.** Deepgram과 Gemini 키를 각자 쓰므로 한 계정의 분당 호출 한도를 나눠 쓰지 않는다. 실측에서 한 명이 분당 7.1회를 썼다(Issue #76).
- **Server 변경 없이 지금 동작한다.** Server는 이미 있는 `POST /meeting/subtitles/mock`과 socket.io broadcast만 쓴다. LiveKit 담당 작업과 통역 작업이 서로를 기다리지 않는다.

## 영향

- **참가자마다 Python 환경과 API 키가 필요하다.** `.env`에 `DEEPGRAM_API_KEY`와 `GEMINI_API_KEY`를 각자 채워야 한다. 개발자가 아닌 참가자는 이 방식으로 참여할 수 없다.
- **화자 정보를 손으로 지정한다.** `--speaker`와 `--name`으로 넣는 값은 LiveKit이 발급한 `participantIdentity`와 자동으로 연결되지 않는다. Client는 `speaker.displayName`만 표시하므로 지금은 문제가 드러나지 않지만, 자막을 참가자와 연결하는 기능이 생기면 맞춰야 한다.
- **회의방 이름을 맞춰야 한다.** Client가 오늘 날짜로 방 이름을 만들므로 파이프라인도 같은 이름을 써야 한다. Issue #81에서 같은 공식으로 생성하도록 했고, Client 파일을 읽어 대조하는 테스트를 두었다.
- **참가자 PC 성능과 네트워크에 의존한다.** 한 명의 환경이 나쁘면 그 사람의 자막만 늦거나 끊긴다. 서버 방식이었다면 한 곳에서 관리할 수 있었다.
- **데모할 때 각자 터미널을 띄워야 한다.** 브라우저만으로 완결되지 않는다.

### 검증된 범위

한 명이 실행하는 경로는 실측으로 확인했다(Issue #72, #76). 첫 자막까지 평균 1194ms, 모델 호출 분당 7.1회, 실패 0건이다.

**여러 명이 동시에 실행하는 경우는 아직 확인하지 않았다.** 자막이 `subtitleId`로 구분되고 Server가 방 단위로 뿌리므로 구조상 섞이지 않아야 하지만, 실제로 두 명 이상이 동시에 말하는 상황은 검증 대상으로 남아 있다.

## 재검토 결과

2026-08-18, 아래 조건 중 첫 번째와 네 번째에 해당해 재검토했다. 배포한 사이트에서
회의에 들어가도 자막이 나오지 않는 것이 결정적이었다. 통역을 회의방 에이전트 한
프로세스로 옮기기로 하고 `docs/ADR/0003-livekit-translation-agent.md`에 기록했다.

## 재검토 조건

- 개발자가 아닌 참가자가 회의에 들어와야 하는 경우
- 참가자 수가 늘어 각자 실행을 관리하기 어려워지는 경우
- 자막을 LiveKit 참가자와 실제로 연결해야 하는 기능이 생기는 경우
- 실사용 배포를 준비하는 시점. 그때는 서버가 트랙을 받아 처리하는 방식으로 옮기는 것이 자연스럽다
